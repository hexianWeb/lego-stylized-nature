## 当前运行时接入

- `src/world/landmarks/landmarkConfig.js` 保存资产测量与默认选址/动画参数，`WorldConfig.landmarks` 提供可编辑配置。目标高度默认 7.6 世界单位，门洞在默认 5.5 飞行高度贯通。
- `landmarkPlacement.js` 只处理地形与选址。每 3×3 chunk 区域一个候选，拒绝水、岸、熔岩、混入火山或高差过大的地形；平台与混合边缘均不进入邻区块的 halo。
- `LandmarkRenderer.js` 只实例化已加载 GLB。每个 slot 预分配四个实例网格，整个世界复用源几何与四个不透明节点材质；无运行时拼砌模型或重复下载。
- `LandmarkPipelineWarmup.js` 在加载页阶段编译和实际绘制相同池对象，等待主/阴影绘制准备队列结束后恢复状态。入场消融的同一 mask 同时用于主画面和阴影。
- 模型导入 `src/assets/sources.js`，随启动资源加载；如果模型缺失会显示资源加载失败，不会悄悄在沙漠留下空平台。
- 已通过选址、平台、邻块 halo、worker 打包、植被避让、模型门洞、池复用、资源释放与预热恢复等测试。实景检查入口与基座摆放；没有据此承诺所有设备上绝对无卡顿。

## 统一美术规则

共享大块积木尺度、轻倒角、哑光塑料、低频色块和少量凸点。先保证游戏视角下的剪影和负空间，再添加细节。每栋建筑以 3–5 个主色为主，避免细栏杆、密集砖缝、悬浮零件和仅靠贴图伪造的支撑。造型宏大主要依靠高度、比例和开阔前景，不靠无限扩大占地。

| Biome | 建筑方向 | 识别轮廓 | 摆放方式 |
| --- | --- | --- | --- |
| 森林 | 巨树观景居所 | 粗树干、分层大树冠、嵌入式房屋 | 岩台基础，树根遮住基座接缝 |
| 秋林 | 风车粮仓 | 四片宽叶、阶梯红屋顶 | 平缓台地；若要风车旋转，叶片独立物体并设轮毂轴心 |
| 沙漠 | 日轮门 | 厚重扶壁、八角通孔、青绿日徽 | 干燥平地，低台阶基座与周围沙坡过渡 |
| 雪地 | 极地灯塔 | 浅色高塔、深蓝灯室 | 岩台承重，积雪只覆盖基础周边 |
| 火山 | 黑岩天文台 | 厚重深色基座、铜色几何穹顶 | 稳定岩台，避开熔岩及活动沟道 |
| 草原 | 气球远征站 | 几何球囊、矮宽停靠塔 | 开阔草甸；球囊连接方式需在模型中成立 |
| 湿地 | 水上驿馆 | 宽檐层叠屋顶、粗支墩 | 建筑楼面高于水面，支墩延伸到河床 |

## 从概念图到模型

1. 在对应地形中评审建筑轮廓、规模和色彩。概念图中的地形、光影、植物不一起交给模型生成器。
2. 确定一张干净主视图，再从同一建筑派生独立的正、左、后、右视图。保持裁切、建筑高度、颜色、结构对应；不能把七格概念板作为单个模型输入。
3. 检查屋顶台阶、门洞高度、基座厚度、侧面进深及装饰位置。侧面有冲突时修正或舍弃，不能把冲突视图硬塞给 Tripo。白底图不是实际 low-poly 网格；面数需在生成后检查。
4. 通过 Tripo 生成单栋建筑。当前 Blender 生成接口只暴露单图参数；要用完整多视图，应使用 Tripo Studio 的多视图流程，或后续接入支持多视图的 API，不能声称单图接口已经用到全部角度。
5. 导出带材质的 GLB。用户减面时优先保住门洞、轮廓、承重结构和屋顶分层；建筑自带低基座，避免携带整片景观地形。
6. 导入后由代码统一尺寸、方向、脚底原点，检查法线/材质/边界，生成实际模型的四向预览，与设计图核对。风车等活动件的拆分和轴心可在此阶段处理。

Tripo 官方要求多视图使用同一对象、匹配风格/比例/光照，并避免极端俯仰角：
https://www.tripo3d.ai/help/features/how-to-use-multi-view-input-effectively

API 的多视图结构须按具体版本映射 front / left / back / right，不能把合成图当成四张输入：
https://developers.tripo3d.ai/en/docs/generation-multiview-to-model/p

## 代码侧负责的贴地方案

- 每种资产配一份小型配置：模型路径、biome、目标高度、真实占地轮廓、入口/通道范围、接地点、基础可埋深、坡度/高差限值、朝向、间隔。外观留在模型中，运行时不再拼砌建筑。
- 选址由世界种子和区域坐标决定，不依赖加载顺序。检查整个基础与入口区域，不能只采样模型中心高度。地形不适合则换候选点，避免靠整栋下沉掩盖穿模。
- 第一版优先选择平缓场地。模型基础与局部小平台衔接，外圈使用同 biome 的自然坡面；只允许基座少量埋入地形，门洞、台阶、主体不得被地形吞没。
- 若需要整平，必须在生成地形表面、AO、植被之前应用确定性的世界坐标平台规则，不能等模型出现后临时改地形。跨 chunk 占地时，邻接 chunk 也读取同一预留/整平规则。
- 入口留出通行区，普通植被/石头避让建筑轮廓并带缓冲距离。飞行门洞需要按实际飞机宽度和飞行高度检查。
- 湿地单独处理水位与河床；支墩允许向下延伸，楼板与水面保持间隙。陆地建筑不使用这一规则。

## 代码侧负责的加载方案

- 不以低面数承诺绝对不卡顿。还需控制材质/子网格数量、纹理大小、首次 shader 编译、GPU 上传、阴影和同屏数量。
- 在玩家到达显示距离前请求资产；按模型路径共享加载 Promise、几何和纹理。反复进入 chunk 不重新下载和解码同一模型。
- 模型下载/解析、GPU 资源准备、展示分阶段进行；限制同时进行的解码/上传/编译任务，避免多栋地标在同一帧全部首次初始化。
- 对支持的压缩格式使用相应解码器；不要只为降低文件大小增加不可控的首次解码成本。准备好低细节版本和同材质纹理的复用方式。
- 地形仍保留原来的逐列升起。整体 GLB 不拉伸、不拆成体素列：基础对应地形稳定且模型就绪后，建筑整体短距升起/消融显现。若以后要求分段升起，需要在模型中保留明确分组。
- 资产未准备好时，地形正常展开；建筑位置保留低成本轮廓或延迟柔和显现，绝不为等待建筑阻塞整片地形。
- 模型缓存设预算并共享引用，反复进出时回收实例但不误释放还被其他实例引用的材质/纹理；长距离探索需要缓存淘汰机制。
- 在目标设备上分别测首次进入、回访、连续穿越多个区域、快速掉头和冷缓存。检查帧时间峰值、绘制调用、纹理/几何内存、首显等待；根据实测设预算。

用户主要交付造型认可后的减面 GLB；材质清理、压缩、贴地、预热、缓存和入场衔接由项目接入阶段处理。先用沙漠一个模型跑通后再批量接入其余六种。
