# 移动端性能：静止绘制与跨区块长帧

## 已落地的优化

- **分开控制清晰度和几何量。** 主指针为触屏类设备（`pointer: coarse`）时，3D 画布最多用 1.5× 像素比和 4× MSAA。额外分辨率按 100 万像素预算分配；逻辑视口本身超过预算时保持 1×。不超过设备原生像素比。积木模型按最多 1× 的参考分辨率选档。移动档继续使用 1024² 方向光阴影、跳过项目的全屏调色和暗角。HUD 仍由浏览器按原生分辨率绘制。
- **减少跨区块时的同步计算。** 云带按行计算实际覆盖范围，只在可能出现云柱的位置采样噪声；云底高度优先读取已生成的远景方块。云柱进入详细地形时保留原来的出现时间，掉头重新进入云带时重新播放。详细地形仍加载 3×3 个区块。

画质在页面启动时选择。`?quality=mobile` 和 `?quality=desktop` 可在同一设备上强制对比渲染设置；云带优化对两档都生效。

## 积木 LOD 和横屏摩尔纹

用相机焦平面上**单个水平凸点投影直径的短轴**选档。所有共用这套几何的地形、水、岩浆实例使用同一档，不是按每块到相机的距离选档。三档首次选择如下；随后在边界两侧使用 15% 的滞回，避免反复跳档。

| 档位 | 参考直径 | 每块三角形 | 砖顶 |
| --- | ---: | ---: | --- |
| LOD0 | ≥ 8 px | 172 | 原模型的四颗凸点 |
| LOD1 | ≥ 4 且 < 8 px | 92 | 六边形凸点，保留高度 |
| LOD2 | < 4 px | 20 | 保留倒角砖身，地形靠材质表现凸点；水不使用地形凸点着色 |

复现条件：默认 seed、HUD 格坐标 `(-735, -319)`、870×400 CSS 横屏、设备 DPR 3、桌面 Chrome/WebGPU 触屏模拟。旧移动档是 870×400、无 MSAA，焦平面凸点约 2.72 px。关闭地形凸点着色或关闭投影强度，水面的点状斜线仍在；临时换成无倒角的平顶砖才消失。原因之一是宽约 0.0063 世界单位的倒角在远处不足一个像素。PC 小窗口仍启用 MSAA，像素比上限也是 2，窗口宽度不能单独解释差异。

当前移动档在同一位置绘制 1305×600，4× MSAA 平滑轮廓和砖缝；凸点投影约 4.08 个渲染像素，几何仍按 2.72 个参考像素选 **LOD2**。地形材质还按接触环和高光边缘各自的像素宽度进行过滤，在格纹本身仍可见时即可淡出更细的高光。对照前后均为 5,269,929 个三角形、347 次绘制（整帧含阴影）；提升清晰度没有把全景升级成几何凸点。桌面 Chrome 的 WebGPU 与 WebGL2 回退路径均验证了该视角。`#debug` 的快照中可对照 `studRenderPixels`、`studLODPixels` 和 `brickLOD`。

## 同路线性能对照

Windows 桌面 Chrome、WebGPU 硬件加速（Lovelace GPU），模拟 390×844 的触屏视口、设备 DPR 3。默认 seed `20260608`，等待九区块和渲染准备队列就绪。从出生点 `[12.8, 5.5, 12.8]` 静止采样 3.5 秒，再以 8 世界单位/秒沿 +X 移动相机和飞机 10 秒，每档均新填充 18 个区块。关闭 `#debug`；帧间隔取连续 rAF 时间戳，CPU 时间取 `Experience.update()` 的墙钟耗时。

| 指标 | 原桌面设置 | 初版移动档（1×、无 MSAA） | 当前移动档 |
| --- | ---: | ---: | ---: |
| 3D 画布像素尺寸 | 780×1688 | 390×844 | 585×1266 |
| 出生点每帧三角形（含阴影） | 15,197,099 | 4,797,995 | 4,797,995 |
| 出生点每帧 draw calls | 296 | 296 | 296 |
| 静止 CPU 帧耗时中位数 | 7.4 ms | 4.2 ms | 4.2 ms |
| 飞行帧间隔 P95 / P99 | 33.4 / 66.7 ms | 16.8 / 17.5 ms | 16.8 / 33.4 ms |
| 飞行中云带更新的最大单次耗时 | 13.3 ms | 6.5 ms | 5.4 ms |

每档均为一次短测，不能用桌面 GPU 的帧率推算真实手机的帧率。相比初版移动档，当前档花费更多像素和多采样带宽；本次飞行 P95 相同、P99 较高。当前档这条路线仍出现过 **50 ms** 的帧间隔，单次主线程区块填充最高 **13.6 ms**；两者未必来自同一帧。

## 真机上如何判断下一步

1. 在同一手机、浏览器和屏幕方向下，分别刷新 `/?quality=desktop` 与 `/?quality=mobile`。等地形稳定后先悬停，再沿同一方向连续飞行；分别记录帧间隔 P95/P99。中档机可先以 P95 ≤ 33.3 ms（30 FPS 的帧预算）为目标。
2. 开发服可用 `/?quality=mobile#debug` → **Performance → Log snapshot** 查看实际 `renderDpr`、`brickLOD`、三角形、CPU/GPU 计时和区块填充耗时。需要可重复的多地貌路线时，在支持 WebGPU 的真机上打开 `/dev/prefab-preparation-validation.html?quality=mobile`，点击 **Run world route**，保存结果后换 `desktop` 再跑一次。
3. **悬停就慢**：先看 GPU 时间与三角形。若减分辨率后仍超预算，优先细分地形实例的裁剪范围、简化阴影投射几何。**只有过边界时顿一下**：先看 `chunk.unpackMs`、`chunk.instancesMs` 和 `prefabBuildMs`。若填充是长帧主因，优先把实例颜色等数据放到 Worker 预计算，或把一次填充分到多帧；现有的 4 ms 调度预算不能打断已开始的填充。
